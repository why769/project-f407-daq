
# 协议帧练习与三个坑（2026-11-22）

## 一、帧格式

```
帧头(0xAA) | ID(1B) | LEN(1B) | DATA(0~8B) | CRC8(1B)
```

最小帧 4 字节（LEN=0），最大帧 12 字节（LEN=8）。总长度 = 3 + LEN + 1。

## 二、为什么要用"字节数组"而不是直接发结构体

直接 `memcpy(buf, &f, sizeof(f))` 或 `uart_send((uint8_t*)&f, sizeof(f))` 在 PC 上"看起来能跑"，但在嵌入式和跨设备场景会出事：

| 问题 | 后果 |
|---|---|
| **结构体填充（padding）** | `sizeof(frame_t)` 可能不等于字段之和，两端布局不一致 |
| **大小端（endianness）** | 多字节字段（如 `uint16_t`）在两端的字节顺序相反 |
| **编译器/平台差异** | 同一结构体在 ARM 和 x86 上布局、对齐可能不同 |
| **变长字段** | 结构体是定长的，`data[8]` 没法表达"只用了 3 个字节" |

**所以协议规定的是"字节序列"，不是"内存布局"**：发送方按字段逐个写字节，接收方按同一规则逐个读。这就是 `frame_pack` / `frame_parse` 存在的意义——它们把"结构体"和"字节流"互相转换，隔离掉平台差异。

## 三、为什么每道检查都不能省

### ① 先检查 `n`，再读 `buf`

```c
if (n < 4) { return 0; }        /* 必须放在最前面 */
if (buf[0] != 0xAA) { return 0; }
```

**原因**：`n` 是"调用者保证有效的字节数"。如果不先卡住，`buf[2]` 可能读到缓冲区外——这是**未定义行为**，可能读到垃圾导致误判，也可能触发 HardFault（在 MCU 上直接死机）。

### ② 限制 `len <= 8`

```c
if (len > 8) { return 0; }
```

**原因**：`f->data` 只有 8 字节。若 `len = 200`（垃圾值/被篡改），后面的拷贝循环会写穿结构体，**覆盖其它变量或栈**——这是缓冲区溢出在嵌入式里的典型形态。

### ③ 检查 `3 + len + 1 <= n`

```c
if ((unsigned char)(3 + len + 1) > n) { return 0; }
```

**原因**：区分"这一帧还没收完"和"帧是垃圾"。串口按字节到达，一次 `read` 可能只收到半帧；此时应返回失败、等下一批数据，而不是拿不完整的数据去算 CRC。

### ④ CRC 校验

```c
if (crc8(buf, 3 + len) != buf[3 + len]) { return 0; }
```

**两边含义不同**：
- 左边：接收方**按同样规则重算**一遍
- 右边：帧里**带过来的**那个字节

**校验范围**是"帧头 → 数据末尾"，**不包含 CRC 字节本身**。范围必须两端一致，否则永远对不上。

## 四、三个坑（这次踩到的）

### 坑 1：`if (...);` 空语句（最危险）

```c
if (len > 8);          /* 分号让 if 空转 */
    return 0;          /* 于是无条件执行 → 函数永远返回 0 */
```

编译器只给 "empty controlled statement" 警告，**不报错**。症状是"函数永远返回失败，但代码看起来没毛病"。

**防法**：`if` 后**永远加大括号**：

```c
if (len > 8) { return 0; }
```

### 坑 2：检查顺序错（先读后查）

```c
if (buf[0] != 0xAA) { return 0; }   /* 此时 n 还没检查 → 越界读 */
```

**规则**：**先用长度信息约束，再访问数据**。任何"指针 + 长度"的接口都适用。

### 坑 3：`main` 里重复定义变量

```c
frame_t tx = {...};   /* 第一次 */
...
frame_t tx = {...};   /* 第二次 → C2374 重定义，编译不过 */
```

复制粘贴时最容易出现。同一作用域内同名变量只能定义一次。

## 五、返回值语义

```c
unsigned char frame_pack(const frame_t *f, unsigned char *buf)
{
    ...
    return (unsigned char)(3 + f->len + 1);   /* 返回"写了多少字节" */
}
```

**踩过的错**：最初 `return crc;`，把校验值当成了长度。调用方拿它去 `uart_send(buf, n)` 会发 49 个字节（全是垃圾），拿它去 `frame_parse` 会越界。

**原则**：函数返回值表示"处理了多少 / 成功与否"，中间结果若要输出，用单独的出参（`f->crc`）。

## 六、可改进项（下一版）

1. **把长度算式抽成宏**，避免到处写 `3 + len + 1`：
   ```c
   #define FRAME_TOTAL(len)  ((unsigned char)(3 + (len) + 1))
   #define FRAME_CRC_IDX(len) ((unsigned char)(3 + (len)))
   ```
2. **给 `buf` 传入容量参数**，在函数内检查 `cap >= 3+len+1`，避免调用方传小缓冲区。
3. **接续缓存解析**：真实串口数据是流式的，需要"环形缓冲 + 滑动找帧头"，而不是假设一次收全。
